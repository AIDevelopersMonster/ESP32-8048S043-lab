# Руководство пользователя

Устройство: **KONTAKTS / ESP32-8048S043 Platform**  
Статус: **живое руководство; уточняется по мере physical validation платформы**.

---

## 1. Назначение устройства

Платформа разделяет системную и прикладную части:

- базовые системные функции находятся в прошивке;
- пользовательский экран `WIDGET` может загружаться отдельно из внутренней файловой системы;
- обновление прикладного виджета не требует перепрошивки всей платформы.

## 2. Органы управления и экран

### Основные системные вкладки

```text
STATUS | OTA | WIDGET
```

- `STATUS` — состояние устройства, сети, версии и раздела прошивки;
- `OTA` — проверка/установка firmware, CONFIRM, ROLLBACK, recovery;
- `WIDGET` — установленный прикладной экран из файловой системы.

## 6. Обновление прошивки OTA

### 6.1 CHECK GITHUB

Проверку обновления можно выполнить:

- с вкладки `OTA` на самом дисплее;
- через web-интерфейс устройства.

Успешная проверка должна показать установленную и доступную версии.

Пример физически наблюдаемого состояния перехода:

```text
installed=0.1.0
available=0.2.1
```

Это означает, что устройство видит стабильный GitHub Release и может перейти к установке.

### 6.2 Installed / Available

Перед обновлением убедиться, что:

```text
Installed: текущая версия
Available: более новая версия
```

Если `Available` не новее `Installed`, установка не требуется.

### 6.3 DOWNLOAD & INSTALL / INSTALL UPDATE

На web-странице нажать:

```text
DOWNLOAD & INSTALL
```

или на дисплее:

```text
INSTALL UPDATE
```

После этого устройство:

1. повторно проверяет manifest;
2. загружает firmware по HTTPS;
3. проверяет размер;
4. проверяет SHA-256;
5. проверяет имя проекта и версию;
6. записывает новый образ в OTA-раздел;
7. выбирает его как следующий boot partition;
8. автоматически перезагружается.

Во время записи firmware не отключать питание без специальной цели тестирования recovery.

### 6.4 Первая загрузка новой версии

После автоматической перезагрузки сначала проверить `STATUS` или serial log.

Для текущего перехода ожидается:

```text
Firmware 0.2.1
running = ota_0 или ota_1
image_state = PENDING_VERIFY
```

`PENDING_VERIFY` — нормальное состояние новой версии до подтверждения пользователем.

### 6.5 КРИТИЧЕСКИ ВАЖНО: не делать reset до CONFIRM

Пока новая версия находится в:

```text
PENDING_VERIFY
```

не нажимать RESET и не выключать питание без намерения проверить rollback.

Bootloader считает неподтверждённую версию испытательной. Если перезагрузить устройство до `CONFIRM`, оно может автоматически вернуться на предыдущую подтверждённую систему.

На текущем переходном этапе старый физический `factory` всё ещё может быть исторической версией `0.1.0`. Поэтому преждевременный reset особенно неудобен.

### 6.6 Обязательная проверка новой версии перед CONFIRM

Для платформы `0.2.1` выполнить минимум:

```text
[ ] STATUS открывается
[ ] OTA открывается
[ ] WIDGET открывается
[ ] touch работает
[ ] Wi-Fi подключился
[ ] IP получен
[ ] web-страница открывается
[ ] CHECK GITHUB выполняется без ошибки
```

При повторном `CHECK GITHUB` на уже установленной `0.2.1` нормальный результат:

```text
installed=0.2.1
available=0.2.1
UP_TO_DATE
```

или эквивалентное сообщение `no newer stable firmware`.

Если повторный `CHECK GITHUB` выдаёт TLS/network error, новую версию пока **не подтверждать** и сохранить serial log ошибки.

### 6.7 CONFIRM

Если предыдущие проверки прошли, нажать:

```text
CONFIRM
```

Ожидаемое состояние после подтверждения:

```text
image_state = VALID
```

С этого момента текущая версия признана рабочей.

### 6.8 Контрольный reset после CONFIRM

Только после `CONFIRM` выполнить обычный reset.

После загрузки проверить:

```text
Firmware 0.2.1
running = тот же OTA-раздел
image_state = VALID
Wi-Fi = online
```

Если после подтверждения и reset устройство снова возвращается на старую версию — зафиксировать serial log; это уже ненормальное поведение.

### 6.9 Что произойдёт при reset до CONFIRM

При reset в `PENDING_VERIFY` bootloader имеет право выполнить rollback к предыдущей рабочей версии.

Это защитный механизм, а не ошибка.

### 6.10 Различие CONFIRM / ROLLBACK / FACTORY RECOVERY

```text
CONFIRM
= принять текущую OTA-версию как рабочую (VALID)

ROLLBACK
= отказаться от текущей неподтверждённой версии и вернуться к предыдущей рабочей

FACTORY RECOVERY
= принудительно загрузить отдельный factory-раздел
```

Важно: пока factory-раздел устройства содержит историческую `0.1.0`, `FACTORY RECOVERY` вернёт именно её. В следующих версиях планируется современный recovery shell с экраном, Wi-Fi и OTA.

### 6.11 Текущий рекомендуемый сценарий 0.1.0 -> 0.2.1

```text
0.1.0
  |
  | CHECK GITHUB
  v
available 0.2.1
  |
  | DOWNLOAD & INSTALL
  v
0.2.1 / PENDING_VERIFY
  |
  | проверить STATUS/OTA/WIDGET/touch/Wi-Fi/web
  | повторить CHECK GITHUB
  v
CONFIRM
  |
  v
0.2.1 / VALID
  |
  | RESET
  v
0.2.1 / VALID
```

Только после этого переходить к тестам файловой системы и виджетов.

## 7. Установка виджета

### 7.1 Где взять `.json`

Тестовые файлы проекта находятся в:

```text
apps/06_OTARecovery/widgets/
```

В текущем эксперименте используются:

```text
widget-demo-a.json
widget-demo-b.json
```

### 7.2 Открыть Filesystem Widget в браузере

Открыть web-страницу устройства и найти раздел:

```text
Filesystem Widget
```

### 7.3 Выбрать файл

Сначала для проверки рекомендуется `widget-demo-a.json`.

### 7.4 UPLOAD & INSTALL WIDGET

Нажать:

```text
UPLOAD & INSTALL WIDGET
```

Успешный результат:

```text
INSTALL PASS
```

### 7.5 Проверить вкладку WIDGET

На дисплее открыть:

```text
WIDGET
```

Для Widget A должны появиться данные о firmware, uptime, IP, heap, PSRAM и RSSI.

### 7.6 Reset и проверка автозагрузки

После того как firmware уже находится в `VALID`, сделать reset.

Widget A должен автоматически восстановиться из:

```text
/storage/widget.json
```

### 7.7 Замена одного виджета другим без firmware OTA

Не обновляя firmware, загрузить:

```text
widget-demo-b.json
```

Экран должен измениться сразу.

Это ключевой тест независимости прикладного HMI от системной прошивки.

### 7.8 DELETE EXTERNAL WIDGET

Удаление внешнего widget не должно удалять или блокировать системные вкладки:

```text
STATUS
OTA
recovery controls
```

## 8. Сохранность данных

- Wi-Fi credentials хранятся отдельно от app OTA;
- widget хранится в `storage` отдельно от app OTA;
- обычный reset не должен удалять widget;
- обычный app OTA не должен стирать `/storage`;
- полный сервисный flash может иметь другой эффект и не является обычной пользовательской операцией.

## 9. Восстановление

### 9.1 Новая версия не подтверждена

Если новая версия работает неправильно до `CONFIRM`, можно использовать rollback-механику.

### 9.2 ROLLBACK

Возвращает предыдущую рабочую OTA-версию/допустимый образ согласно состоянию bootloader.

### 9.3 FACTORY RECOVERY

Принудительно выбирает отдельный factory-раздел.

Текущее переходное ограничение:

```text
factory = историческая 0.1.0
```

Поэтому обычный пользователь не должен нажимать `FACTORY RECOVERY` без необходимости.

В следующих системных версиях factory должен стать современным recovery shell.

## 10. Типовые неисправности

| Симптом | Что проверить | Действие пользователя | Когда нужен системный программист |
|---|---|---|---|
| Не подключается Wi-Fi | SSID/пароль/режим AP | повторить provisioning | повторяющиеся reset/errors |
| CHECK GITHUB выдаёт ошибку | интернет/сеть | повторить после восстановления связи, сохранить serial | TLS/memory error повторяется |
| Widget не принимается | JSON/версия schema | выбрать корректный файл | корректный файл стабильно reject |
| Widget пустой после reset | наличие install PASS | установить повторно | autoload failure |
| После update вернулась старая версия | был ли CONFIRM | установить снова и CONFIRM | rollback происходит после CONFIRM |
| После FACTORY RECOVERY появилась 0.1.0 | текущая версия factory | это ожидаемо на переходном этапе | factory будет модернизирована отдельно |

## 11. Безопасность действий

- не отключать питание во время firmware write без необходимости специального теста;
- не делать обычный reset в `PENDING_VERIFY` до принятия решения CONFIRM/ROLLBACK;
- не использовать случайные/непроверенные widget JSON в ответственных установках;
- не публиковать Wi-Fi пароль;
- destructive recovery/service procedures выполнять только по отдельной инструкции.
