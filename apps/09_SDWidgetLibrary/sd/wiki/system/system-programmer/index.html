Boot order

NVS credentials, internal storage, Widget Runtime and OTA initialize first. SD manager initializes without mandatory boot-time mount. Network stack and services start before the display shell and HTTP server. A missing SD card must not block SYS/recovery or the persisted widget.

SD manager

Current physical mapping: CS GPIO10, MOSI GPIO11, CLK GPIO12, MISO GPIO13. Initial validated SPI frequency is 10 MHz. Automatic formatting is disabled.

Web Help

The HTTP layer exposes four exact Help handlers: /help, /help/system, /help/app and /help/style.css. The handler mounts SD on demand if necessary. The landing page scans package manifests and exposes only packages declaring documentation.entry = html/index.html.

Serial service 0.3.5 → 0.3.7

Platform 0.3.5 adds the generic serial service used by the SD package usb-serial-terminal. Stage 1 deliberately reuses the existing UART0 console path instead of independently reinitializing the UART driver:

PC <-> USB <-> CH340C <-> UART0 <-> serial_service <-> Widget Runtime

The service publishes serial.rx_text, serial.rx_bytes, serial.tx_bytes and serial.state. Platform 0.3.5 introduced serial_send_test and serial_clear; Platform 0.3.7 adds the generic serial_send_text action used by interactive SD applications. It accepts text supplied by a Widget Runtime textarea and appends CRLF before writing to the existing stdout/UART0 path. Because UART0 is also the ESP-IDF console, normal log output is expected on the same PC terminal.

Sample A, 2026-09-22: the onboard USB-UART route was physically exercised in both directions. Позднее P1 был физически подтверждён как технологический/service UART0; он намеренно не классифицируется как application/field UART.

Platform 0.3.9: transport architecture

HMI -----------+
UART0/P1 ------+
Web browser ---+--> command/service layer --> providers --> hardware
BLE -----------+
Mobile app ----+

UART0/P1 — технологический/service transport через CH340C, 115200 8N1. Он не считается полевым пользовательским UART. UART1 GPIO17/18 — текущий полевой transport для Modbus RTU через внешний automatic-direction RS485 transceiver.

BLE App16: native ESP-IDF NimBLE peripheral KONTAKTS-8048; service FFF0, command FFF1 WRITE, response FFF2 READ. Входящие строки идут в тот же command_service_execute(), что и UART0/Web. BLE transport не знает Modbus-регистров MA01.

Platform 0.3.9: memory/coexistence hardening

Физический тест App16 выявил не логическую ошибку BLE, а дефицит/фрагментацию внутренней DMA-capable RAM при совместном старте RGB/LVGL, Wi-Fi/HTTP, BLE и OTA. Принята следующая политика:

  • RGB/LVGL display получает ресурсы до optional BLE init;
  • LVGL partial draw buffer размещается в PSRAM;
  • NimBLE host allocations переводятся в external RAM, где это поддерживается;
  • 16 KiB OTA worker stack создаётся в PSRAM;
  • RGB bounce buffer остаётся во внутренней DMA-capable памяти;
  • ошибка optional BLE не должна блокировать загрузку платформы.

PHYSICAL PASS, 2026-09-29: после этих изменений одновременно работают HMI, SD, HTTP/Web, Wi-Fi, BLE, UART0 service и MA01 UART1/RS485. GitHub OTA CHECK также проходит после переноса OTA worker stack.

Security

SD HTML is untrusted content relative to platform control APIs. Help responses therefore disable script execution, forms, frames, objects and fetch/connect through Content Security Policy. File paths are not supplied directly by the browser: system pages use a fixed allow-list and package names use the same restricted ASCII directory rule as SD Manager.

Firmware update rule

Application-specific functionality stays on SD whenever existing services and capabilities are sufficient. Platform firmware changes only for a genuinely reusable capability, provider, driver, runtime primitive or security/recovery change.

Known current limits

  • manifest requirements such as minimum_platform and requires.services are not yet enforced by SD Manager;
  • catalog limit is currently 24 entrypoints;
  • entry file names are direct basenames;
  • offline /UPDATE full flash-write path remains an acceptance item;
  • the App09 display source is still generated by CMake from the proven App08 renderer;
  • generic textarea and standard LVGL 9 keyboard primitives are implemented from Platform 0.3.7; command history, configurable line endings, HEX mode and a custom keyboard remain LAB-03 work.

Version boundary

Platform 0.3.3 introduced browser-only SD Help. Platform 0.3.5 added the reusable serial monitor service. Platform 0.3.7 added generic textarea, LVGL 9 keyboard and serial_send_text. Platform 0.3.9 adds the BLE transport and memory/coexistence hardening while preserving the same provider/service boundary. No long-form Help UI is added to the 800x480 display.
